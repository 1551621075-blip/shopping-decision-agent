# 购物决策 Agent：本地 Demo／测试版

独立的中文笔记本选购应用：模型逐轮选择补问、查询、比较、评估和推荐；程序负责预算、事实、权限与确认。使用 **16 款原创合成笔记本**，不抓取真实价格、不下单、不付款，不把合成指标当真实测评。

> 页面、API、CLI 和八工具循环已实现；637 项自动化测试、30/30 与 8/8 TEST 场景、最终源码外锁定安装通过。最终两轮真实页面业务闭环通过，但严格整体验收均因 Chrome 后台连接尝试失败（各 5 次，全部被阻断，转发 0）。真实模型核心场景未运行、人工解释审查未完成；TEST 固定策略不代表真实模型自主能力。各项结果及限制见 [验收记录](docs/validation.md)。

## 它能做什么

- 根据已有预算和用途临时查询，不要求先填完整问卷。
- 展示模型提议的偏好，用户核对卡片或编辑表单后明确确认。
- 对确认条件做硬筛选；总价包含运费，未知硬规格不能算满足。
- 比较最多 6 款候选，展示版本化整数评分、权重及未知项。
- 推荐满足硬条件的候选；选非最高分时，必须有相对最高分候选更优的实际指标取舍。
- 修改预算、商品涨价/售罄、目录变化或证据过期后，旧结果失效，不默默沿用。
- 取消或修改偏好时隔离在途模型输出；未知调用保留账本，人工对账后只允许新消息启动新轮次。

## 为什么不只是固定工作流

实际模式是 `agent → guard → tools → agent`。模型一次给出一个工具及参数，后端执行后把实际结果放入下一次请求；模型可以据此改变行动。程序没有强制“先补问、再搜索、最后推荐”的整套顺序。

筛选规则固定，是为了不让模型更改预算或编造规格。规则固定并不妨碍 Agent；但 **TEST 关键词策略本身不是模型自主决策**。只有显式连接本地模型并检查真实轨迹，才能验收这一点。

## 项目结构

- `src/shopping_advisor/catalog.py`：合成目录校验、硬条件、透明评分。
- `actions.py / storage.py`：用户确认、版本、事务、幂等回执及证据失效。
- `agent.py / provider.py / service.py`：LangGraph 循环、HTTP、预算、隔离与恢复。
- `tools.py`：八工具及后端事实卡。
- `api.py / cli.py / templates / static`：中文页面与本地服务。
- `evals / scripts / tests`：冻结场景、验收驱动和自动化。
