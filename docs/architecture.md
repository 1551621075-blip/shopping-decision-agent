# 购物决策 Demo 领域契约

范围：原创合成笔记本目录，不查实时价格、不下单、不接支付。所有金额为 CNY 整数分，总成本=商品价格+明示运费。目录数值是Demo输入，不是测评或真实续航承诺。

## 偏好与确认

- 客户身份由服务端令牌确定，Alice/Bob相互隔离；operator只能维护合成价格/库存与未知调用对账。
- 模型可从首条消息生成临时搜索条件，无需先填问卷。正式推荐只绑定已确认偏好。
- 偏好包含硬预算、最低内存/存储、可选重量/续航/独显/系统硬条件；用途和排序偏好仅影响软评分。
- 模型提出偏好草案不修改生效偏好。用户确认绑定草案ID/version/hash/action_id；或在页面编辑表单后显式提交完整偏好。自然语言“好的”不算确认。
- 新消息取消旧待确认草案。偏好确认/编辑增加偏好revision并取消在途轮次；迟到响应仍记用量，但不能产生推荐。新消息等待在途调用结束或未知对账。
- 同action_id同请求返回原回执，异请求冲突。旧版本/hash/过期草案拒绝。
- 页面编辑绑定显示时的版本；轮询不自动重基未提交内容。冲突时显式重新加载，读取失败时旧卡显示未核验、禁确认；恢复读取后按后端当前有效性显示。

## 查询、评分与推荐

- search_products可使用未确认的临时偏好；已确认后不能以工具参数暗中放宽预算。比较必须来自同次有效查询，正式评估必须匹配当前已确认偏好。
- 目录快照必须在24小时内；证据/评估15分钟内。未知硬规格不是满足条件，售罄不合格，无合格项就说明冲突，不能自动加预算。
- 查询记录绑定完整目录hash、偏好revision与条件；新增商品、价格、库存或偏好改变均使旧查询/评估/推荐失效。刷新只读，不自动重新调用模型。
- 评分是版本化确定性整数规则，公开组成和权重。只评价本次比较的候选，不声称全市场最优。
- 模型可选非最高排序的合格商品；必须选择可核对的比较指标，至少有一个相对最高排序项更优的实际取舍。金额、指标值、比较方向和得分由后端填入，不采信模型自填数字。
- 来源核对递归贯穿查询→比较→评估→推荐；引用环及过深链拒绝。使用证据时重新计算搜索、比较和评分，内容不一致不能继续推荐。证据寿命也受原始商品剩余快照时效约束。
- 推荐理由由模型选择的指标+后端事实模板组成；自由模型文字仅在轨迹中保留，不直接发布为事实。

## demo-v1 评分规则

所有范围截断后用整数除法向下取整，不使用真实跑分或候选相对排名。

- CPU/GPU 的合成输入范围为 0–100；内存按 4–32 GB、存储按 128–1024 GB 线性归一化，超过上界不额外加分。
- performance = CPU 50% + GPU 30% + 内存 15% + 存储 5%。
- portability 按 500–5000 克反向归一化；battery 按 30–1440 分钟正向归一化。未知软指标记 0，并列入 unknown_specs。
- value = `(预算 - 含运费总价) * 100 // 预算`，表示预算余量，不代表市场性价比或质量。
- 用途基础权重合计 60：office=12/15/15/18，coding=24/12/12/12，creative=30/9/9/12，gaming=36/6/6/12（顺序为性能/便携/续航/预算余量）。用户选择的优先项再加 40，总权重 100。
- 总分为四维分数的加权整数平均。排序依次为分数降序、含运费总价升序、商品 ID 升序。只评估本次比较列表，不扩称全目录最优；TEST 策略只取查询顺序中的前 6 项。

## 运行接口

包名shopping_advisor，CLI shopping-advisor；Store/Runner使用独立SQLite和venv，不跨项目import。

Actions接口：create_session、message、cancel、set_preferences、decide_proposal、view、update_product；内部customer_session、_related、_freeze供Runner/Tools使用。会话字段control=bot、control_epoch、active_run、messages、tool_count、blocked_unknown、preferences、preferences_revision。run字段与已验证本地客服运行时通用部分一致。

Tools.execute返回{result, terminal}。八工具read_context/ask_shopper/propose_preferences/search_products/compare_products/evaluate_shortlist/recommend/respond。等待偏好确认不会自动继续，确认后新消息启动新轮次。

模型调用事务外执行；调用前记账，未知用量阻断；取消不追回HTTP或token。TEST关键词演示仅证明编排，真实HTTP需用户显式数字loopback端点和model ID，不发现或启动模型。

- `metrics` 中 token 是已知小计；在途调用另列 `pending_calls`，仍未知列 `unknown_calls`，两者任一存在时 `usage_complete=false`。
- HTTP Provider 每次只发一个请求；运行时只对用量可靠的 `provider_invalid` 格式错误反馈重决策，其它已知 HTTP 错误结束本轮，不自动重复请求。可能已发送但结果未知时必须对账。
- Service 用短生命周期锁串行化“确认未关闭→保存消息→投递”，关闭时锁外等待已接收任务排空，再释放实例锁。多线程同时关闭也等待真实完成。
- `Runner.recover()` 仅用于取得实例锁后的启动恢复，不支持与活跃调用并用；它不是页面可调用的恢复入口。操作员使用单独对账 API。
- 数据库通过 URI 编码保留本地路径的字面含义，`?`、`#`、`%` 不得改变 SQLite 参数或写入邻接路径。

本文件是实现契约，不是验收通过记录。冻结30场景、8真实模型核心、自动化/浏览器/安装与人工解释审查分开报告。
