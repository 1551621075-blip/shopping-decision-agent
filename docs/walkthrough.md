# 从一句话到推荐：模型与程序各做什么

以下是应验收的业务过程，不是已经完成的真实模型成绩。TEST 模式采用固定关键词策略；真实模型可以选择不同的合法工具顺序。

## 1. 用户说出需求

例如：**“预算 6000 元，主要写代码，至少 16GB 内存和 512GB 存储。”**

客户身份来自登录令牌，不由消息或模型决定。消息提交生成一个 run，刷新页面不会生成 run。模型获得本人的消息、已确认偏好、工具约束和预算。

模型可以先补问，也可以用现有信息临时查询。临时查询不修改用户的有效偏好，结果标记为未确认。

## 2. 模型提出条件，用户确认

`propose_preferences` 的输入是完整结构化偏好，不是商品或购买指令。后端保存草案：例如 `budget_cents=600000`、`use=coding`、`min_ram_gb=16`、`min_storage_gb=512`。

用途只是评分偏好，不会被偷偷转换为“必须独显”等硬条件。用户在卡片上检查预算、每一项硬条件、软评分优先级后点击确认；也可以直接在完整表单里编辑并提交。默认条件也会展示，不是后台暗中添加。

确认绑定草案 ID、版本、内容摘要和操作 ID。仅聊天说“好的”不算确认。确认后只保存条件，不下单、不自动再次请求模型；用户发新消息才继续。

## 3. 查询返回事实，不返回想象

`search_products` 由程序检查当前 16 款原创合成商品：

- 商品价 + 运费是否在预算内？
- 库存是否大于零？
- 内存、存储及用户明确设置的其他硬条件是否满足？
- 需要的规格是否已知？
- 商品快照是否未满 24 小时？

查询 Observation 含完整合格商品、排除原因、当次条件、是否已确认和目录版本。模型在下一轮实际看到这个结果，而不是凭之前的聊天猜可选项。

## 4. 模型选比较对象，程序计算

`compare_products` 只能引用当前有效查询中的 1–6 款商品；不能加入不存在、售罄、超预算或来自其他会话的商品。

`evaluate_shortlist` 需要已确认偏好。程序返回每个候选的含运费总价、四维组成、权重、未知规格及 `demo-v1` 得分。所有金额是整数分，权重总和为 100，分数是 0–100 的整数。

这里只比较选中的候选，不能称“全网最佳”。未知软指标按零计分是本 Demo 的保守规则，不表示真实产品能力为零。

## 5. 模型选择推荐与取舍

`recommend` 由模型给出评估 ID、商品 ID、要展示的指标和比较对象，不接受自填价格或分数。

- 推荐最高排序项：可以直接引用其真实指标。
- 选择其他候选：至少要有一项相对最高排序项更好的已知指标，例如更轻或更便宜。程序验证比较方向和数值。

后端重新验证整条查询→比较→评估引用链，从权威目录重算；再用事实模板生成推荐卡。模型自由文字只保留在轨迹中，不直接作为报价、下单状态或测评结论发布。

## 6. 用户降低预算，或商品变化

用户明确将预算改成 100 元后，偏好 revision 增加，旧推荐失效。在途 run 被取消，迟到动作不能写回，但已消耗用量仍保留。

接下来用户发“重新比较”。搜索无合格项，就展示排除原因并询问要调整哪项条件。系统不会为了给出推荐自动提高预算。

operator 可以在合成目录面板改变价格或库存，用于本地演示；任意目录变化也使旧查询、评估和推荐失效。页面只标失效，不偷偷调用模型重做。

## 7. 如果请求中断

调用前写 `started` 账本，HTTP 在数据库事务外执行。结果或用量未知时阻断会话，不当零费用，也不盲目重试。

operator 根据实际可核验记录对账。对账只解除阻塞，不重放旧动作、旧 run 或旧计划；客户再发新消息才能继续。取消本地 run 不等于远端 HTTP 被取消或 token 被退回。

## 判断“是不是 Agent”的关键

不是看工具多不多，也不是看有没有固定规则，而是看：**下一步任务行动是否由模型根据实际 Observation 决定。**

本项目提供这个运行架构，同时保留硬约束。TEST 演示只能证明执行和状态链路；没有真实模型轨迹时，不应宣传已经验收了模型自主决策能力。
